MIL Underwriter Workspace — Stabilization Audit

Full-system audit, bug fixes, and production-readiness assessment

Branch: 002-underwriter-workspace Date: 2026-07-06 Scope: specs 001–004
Bottom line: The reported “auth bug” was never an auth bug. The real defects were five separate, independently-discovered integration gaps, all now fixed and verified against a live, running system (not just unit tests). 1. Issues found, root cause, and fix

1.1 “Blank main content” / apparent auth bug

FixedNot an auth bug

Reported as: navbar shows “Dev Admin,” main content blank, GET /v1/applications returns 401.

Root cause: Authentication is correct end-to-end (verified live: no token → 401, Bearer dev → 200; the deep-linkable Application Workspace route already attached the token and rendered correctly). The actual defect: frontend/src/app/Root.tsx, the component behind the / route, was a literal Phase-1 placeholder — return <h1>MIL — Underwriter Workspace</h1> — that fetched nothing. The 401 the user saw was a real, correctly-functioning security control on a route nobody had wired a fetch into yet, not a broken one.

Fix: Root.tsx now fetches the existing (unfiltered) GET /v1/applications list and redirects to the first application’s Workspace, with proper loading/error/empty states. This does not implement the Application Queue (User Story 2) — no search, filter, sort, or pagination UI was built; it is a real, working entry point matching spec 002’s own stated MVP path (“reachable via a direct link”).

Architectural impact: None. One new bootstrap-only query hook (useApplications, explicitly documented as not for queue reuse); no backend changes.

1.2 Worker crash on evidence replay (ADR-008 violation)

CriticalFixed

Reported as: extraction worker crashes reprocessing an already-extracted document; unique constraint fires, worker crashes, job requeues, crashes again — a permanent crash loop.

Root cause: ADR-008 requires replay to be a no-op. Every one of the five pipeline workers (OCR, Extraction, Finding, Policy, Review) had the same structural gap: an up-front exists_for_* check (a first line of defense, but race-prone under concurrent workers) followed by an unprotected database write with no exception handling. A uniqueness violation at insert time — whether from a true replay or a race between two workers — propagated as an unhandled IntegrityError straight out of the job handler.

Fix: every repository gained a save_if_not_exists-style method using a SQLAlchemy SAVEPOINT (session.begin_nested()): the insert is attempted, and an IntegrityError is caught and treated as proof-of-prior-completion, returning False instead of raising. Each worker’s service layer now returns a (entity, created) pair; outbox events (which would otherwise duplicate) are only published when created is True, while step-completion and next-step dispatch still proceed unconditionally (queue-level idempotency keys already make redundant dispatch safe).

Verified: 1823 backend tests pass, including new collision-simulation tests per worker (TestConcurrentReplayCollision) that force a save_if_not_exists collision and assert the worker returns a normal outcome with zero duplicate events — not an exception.

1.3 Worker processes die permanently on any unhandled exception

CriticalFixed

Discovered live, not from a report: while running a real document through the pipeline, the Policy worker hit a different, legitimate error (no active Policy Pack for the tenant — itself a real gap, see 1.4) and the entire worker process exited. Every one of the five workers ran an identical bare while True: process_next(...) loop with zero exception handling at the loop level — the ADR-008 fix above only covers the one exception type (IntegrityError) it specifically targets. Any other unexpected failure (a missing dependency, a malformed payload, a genuine bug) silently kills that worker process, halting every other application’s processing on that step, indistinguishable from the process being down.

Fix: added workers.bootstrap.run_forever, a shared polling loop that wraps each process_next call in try/except Exception, logs, and keeps polling — mirroring the API layer’s own existing top-level exception handler in mil.api.errors. All five workers’ main() functions now call it instead of hand-rolling the loop.

Verified: new TestRunForever suite proves the loop survives repeated handler exceptions and keeps processing; confirmed live by intentionally reproducing the missing-Policy-Pack crash and watching the worker log the error and keep running.

1.4 No way to create or activate a Policy Pack — Policy step always fails in a fresh environment

CriticalDocumented, not fixed

Discovered live while tracing the pipeline end-to-end: the Policy worker requires an active Policy Pack for the tenant, and PolicyService.create_pack/activate_pack/add_rule are fully implemented and tested — but no HTTP endpoint exists anywhere to call them (confirmed: no mil/api/v1/policy.py, no references in main.py). In any environment without direct database or script access, every application’s Policy step fails forever.

Why not fixed now: building a Policy Pack admin endpoint is new product surface, not a stabilization fix, and risks exactly the scope creep the user explicitly ruled out (“do not implement any additional user stories”). Verified the rest of the pipeline works once a pack exists by creating one directly via the existing service (an operational action, not a code change).

Recommendation: decide deliberately — either a minimal admin endpoint, or a seed script run as part of environment setup — before the next demo.

1.5 Findings could never be verified or overridden — a fresh finding always 422s

CriticalFixed

Discovered live: calling POST /v1/findings/{id}/verify on the very first finding generated end-to-end returned 422 INVALID_STATE_TRANSITION: “Cannot transition ReviewSession from ‘PENDING_REVIEW’ to ‘APPROVED’.” This is not an edge case — it is the very first thing a reviewer does with a new finding.

Root cause: the Review state machine only permits APPROVED/REJECTED/OVERRIDDEN from IN_REVIEW, never directly from PENDING_REVIEW — by design (ReviewSession.assign_reviewer already exists and is tested to make that transition). But nothing in the HTTP layer ever called it: FindingReviewActions.verify/override called approve_finding/override_finding directly, which only work from IN_REVIEW. This had zero test coverage anywhere in the suite — the gap was invisible until a real end-to-end call exercised it.

Fix: FindingReviewActions gained _ensure_in_review, which auto-assigns the acting user as reviewer (transitioning PENDING_REVIEW → IN_REVIEW) immediately before verify/override proceed — matching how underwriting queues work in practice (the first person to act on a pending finding becomes its reviewer). escalate is untouched: PENDING_REVIEW → ESCALATED was already a valid direct edge.

Verified: new test file exercises the real FindingReviewActions/ReviewService/ReviewSession objects (not mocks); confirmed the test fails without the fix (reverted it temporarily to prove the regression is real) and passes with it. Confirmed live: verify now returns 200 with "state": "verified".

1.6 API process can crash on Finding review actions — incomplete model registration

CriticalFixed

Discovered live, immediately after fixing 1.5: the corrected verify call still failed, now with a 500 and sqlalchemy.exc.NoReferencedTableError: ... 'orchestrator.workflow_runs'. SQLAlchemy resolves a mapped class’s foreign keys lazily, against whichever tables have actually been imported by that point in the process’s life. Worker processes already had a _register_all_models() helper for exactly this reason; the API process (main.py) never had an equivalent — it relied on the accident of routers transitively importing every model module, which turned out to be false the moment a write path touched a table nothing else happened to import.

Fix: extracted the registration helper into a shared mil.kernel.model_registration.register_all_models(), called from both workers.bootstrap.build_worker_context (unchanged behavior) and main.py’s lifespan handler (new). Neither process now depends on the other, or on import-order luck.

Verified: full backend suite green; confirmed live — the same verify call now returns 200.

1.7 Duplicate uploads silently doubled an application’s evidence

HighFixed

Reported as: undefined behavior on repeated uploads — explicitly flagged for a decision.

Root cause: DocumentService.ingest_document never checked for an existing document with the same content hash. Re-uploading the identical file to the same application created a second Document row with its own document_id; since the pipeline’s replay-safety is keyed on document_id (not content), OCR and Extraction ran again in full, doubling the evidence pool feeding Finding generation.

Decision: reject byte-identical re-uploads to the same application with 409 Conflict, naming the existing document. Uploading different bytes (a corrected re-scan) is unaffected. Chosen over silent no-op or versioning as the most conservative option: it surfaces the duplicate to the uploader immediately rather than silently skewing evidence, and needs no new domain concept (document versioning/supersession does not exist today).

Verified: new repository + service test coverage; confirmed live — re-uploading the same file returns 409 naming the original document.

1.8 Dev-seed user ID fails frontend UUID validation — crashes Audit Timeline and Documents tab

HighFixed

Discovered live while screenshotting the real UI: the Overview tab’s Audit Timeline and the Documents tab both showed “Could not load…” despite the API returning 200 with valid data.

Root cause: the backend’s development identity constant, DEV_USER_ID = UUID("00000000-0000-0000-0000-000000000001"), is not RFC 4122-compliant (no valid version/variant nibble). Every audit event and document record attributed to this actor carries that ID as actor_id/uploaded_by. The frontend’s Zod schemas correctly use strict z.uuid() validation — the same rigor the test suite’s own MSW fixtures had already been fixed to satisfy once before — and correctly rejected it, throwing inside the query and tripping the error boundary.

Fix: DEV_USER_ID/DEV_TENANT_ID now use valid version-4 nibbles (00000000-0000-4000-8000-...0001 / ...0002), a single source of truth shared by dev_seed.py.

Residual effect: data created before this fix in this local database still carries the old, invalid ID and will keep showing this error until re-created — a one-time local dev-data artifact, not a code defect. Confirmed live: a freshly created application’s audit trail and documents both render correctly.

3. UX review — honest critique

Screenshots below are the actual running application, not mockups.

Evidence tab

Overview tab, before the audit-timeline fix

Would a professional underwriter enjoy this? Not yet, but the foundation is closer than it looks — the confidence indicator, AI-generated badge, and evidence chips are genuinely good primitives. Concrete, functional gaps a reviewer would hit immediately:

  • No page chrome or product identity. The top bar is only a user menu; there is no product name, no application switcher, no breadcrumb back to a list. A user who lands here has no way to get to a different application without editing the URL. This is the single biggest gap between “a working page” and “a product.”
  • The application header shows a raw UUID (“Application 3f44fe7a-d3ac…”) instead of the LOS reference or loan number the application already has. An underwriter identifies work by loan number, never by UUID.
  • Findings are laid out for one item, not a queue. Real applications generate multiple findings; there is no visible list/summary chrome (count, filter by confidence or status) once there is more than one card on the page — untested because the live app only had one finding.
  • Evidence table has no source linkage in view. Each row shows only a field/value pair — no visible link back to the source document or page, which is the entire point of provenance-first evidence in a mortgage tool. (It may exist in code/hover state; it did not appear in the static render.)
  • Verify/Override/Escalate buttons render disabled by default with no visible reason why (in this screenshot, permissions were fine) — an underwriter would not know if that’s a permissions issue, a workflow-state issue, or a bug.
  • Generous whitespace, but underused. Each tab is a single card floating in a mostly-empty 1440px canvas. This reads as unfinished rather than minimal — Linear/Stripe-grade density uses the horizontal space for secondary context (metadata rail, related items), not just margin.

What’s already right and shouldn’t change: the AI-generated/Verified badge pairing, the confidence indicator glyph, evidence-chip provenance tags on the finding card, and the plain-language empty/error states (no raw stack traces surfaced to the user anywhere, even during the bugs found in this audit).

Recommendation: do not do a visual redesign pass yet. Fix the application-switcher/identity gap first (it blocks basic usability, not aesthetics) and defer density/polish work until a second application with multiple findings can be used to test the list states honestly.

5. Remaining technical debt

  • No Policy Pack admin surface (1.4) — a deliberate scope decision to make, not an oversight.
  • No dead-letter visibility. A job that exhausts its retry budget is dropped silently (confirmed during this audit’s own testing) — no operator-visible record, no replay mechanism.
  • Stale local dev data referencing the pre-fix, non-compliant dev user ID (1.8) will keep erroring in the Audit Timeline/Documents tab until re-created.
  • Frontend bundle size warning on the Application Workspace chunk (512KB) — not investigated in this pass.
  • Storybook and the project’s Playwright E2E suite were not run in this audit.
  • UX gaps listed in Section 3 (no application switcher, raw UUID in header, findings-list-at-scale untested).

6. Production-readiness

6.5 / 10

The core pipeline is now demonstrably correct and resilient end-to-end against real providers — a meaningful jump from where this session started (a worker crash loop, a route that fetched nothing, and a review action that could never succeed on a fresh finding). The score is held back by one deliberately-undone item (Policy Pack administration, 1.4, which blocks the pipeline from completing unassisted in any fresh environment) and the UX gaps in Section 3, not by correctness concerns in the code touched this session.

7. Recommendation

Ready to resume feature development, conditionally. That is the one remaining item that stops the product from working unassisted. Everything else found this session is fixed and verified live. The UX gaps are real but are backlog items, not blockers — they do not represent broken functionality.
